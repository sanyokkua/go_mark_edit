# Internationalization (i18n)

GoMarkEdit is internationalization-ready: every user-facing string flows through an i18n layer, English
ships in v1, and adding a locale needs only a resource file (DD-35). Refines
`01_FUNCTIONAL_REQUIREMENTS.md#fr-i18n`. Implemented in the `i18n/` module.

## i18n layer

All user-facing text is retrieved through a lightweight i18n layer's translation function `t(key)`
(the `i18n/` module, `i18n/index.ts`). No component hard-codes a display string; menus, dialogs,
tool-tips, status-bar labels, banners, and error/toast messages all resolve keys through `t()`. The
active locale is initialised at startup and can be selected in the Settings Language group
(`11_SETTINGS.md#language-group`). Because the app is offline (DD-32), all locale resources are bundled;
nothing is fetched at runtime.

## String catalog

Strings live in a per-locale resource bundle keyed by stable, namespaced ids (e.g. `menu.file.open`,
`status.autosave.on`, `banner.remoteContent.title`). v1 ships **`locales/en.json`** as the canonical
catalog; it is the reference that any new locale mirrors. Keys — not English text — are the stable
identifiers stories and tests reference, so wording can change without breaking lookups. The catalog is
flat/namespaced JSON so it is diffable and translator-friendly.

## Adding a locale

Adding a language requires **only a new resource file** and no code changes (DD-35, EC-I18N-2):

1. Copy `locales/en.json` to `locales/<lang>.json` (e.g. `de.json`).
2. Translate the values, keeping the keys identical.
3. Register the locale in the language list (data-driven, from the bundled resource files).

The UI then offers the new language in the Settings Language selector. No component, layout, or logic
change is permitted as a condition of adding a locale — if one is needed, that is a bug in the i18n
layer, not the locale.

## Formatting

Locale-sensitive formatting (numbers such as the word count, dates in the About/logs, and any
pluralization) goes through the i18n layer's formatting helpers rather than hard-coded formats, so a new
locale formats correctly from its resource data. Interpolation uses named placeholders in the catalog
values (e.g. `"status.words": "{count} words"`), never string concatenation in code, so word order can
change per language. Text direction is LTR for the shipped English locale; RTL support is not a v1
requirement but the token/layout model must not preclude it.

## Edge cases

- **EC-I18N-1** — A missing translation key falls back to English (or the key itself), never a blank
  label.
- **EC-I18N-2** — A new locale is added by dropping in a resource file only; no code change.
- **EC-I18N-3** — Long translated strings must not clip actions; controls tolerate overflow (wrap or
  ellipsize) while keeping targets reachable.
