# GoMarkEdit working instructions

GoMarkEdit is a native, offline-first Markdown editor and viewer. One Wails v2 binary contains a Go
backend and a React frontend in the operating system's webview. The backend owns application state,
file I/O, persistence and native integration; the frontend presents and commands that state. Markdown
files remain the user's source of truth.

The product makes no background network request, telemetry call or automatic-update request. Any
future provider request must be explicitly initiated by the user and governed by its own change.

## Specification workflow (OpenSpec)

OpenSpec is the repository's only specification-driven workflow.

- `openspec/specs/<capability>/spec.md` describes what the application does today.
- `openspec/changes/<name>/` holds a proposed change (proposal, design, delta specs, tasks);
  finished changes move to `openspec/changes/archive/`, which also holds the history of the earlier
  numbered features.
- `openspec/config.yaml` holds the project context and engineering rules, and OpenSpec injects them
  into the generated instructions. Follow the output of `openspec instructions` for each artifact.

Propose or plan a change before implementing it: `/opsx:propose` (or the `openspec-propose` skill),
`/opsx:explore` to think first, `/opsx:update` to revise artifacts, `/opsx:apply` to implement tasks,
`/opsx:sync` to merge delta specs, and `/opsx:archive` once the work is implemented and verified.
`openspec validate --all --strict` must pass. The generated `.agents/` and `.claude/` skills and
commands are tool output; refresh them with `openspec update`, do not hand-edit them.

If the specs and the code are silent or ambiguous, stop and surface the question with a recommended
default. Do not invent behaviour, weaken a requirement, or edit a spec merely to make an
implementation or gate pass.

## Authority

- `openspec/specs/` and the active change under `openspec/changes/` — product behaviour.
- `docs/index.md` — project overview, data flows, interfaces, configuration, operations and scope.
- `docs/architecture.md` — owners, consumer inventories, lifecycle, persistence, verification
  walkthrough and durable decisions. A new durable decision supersedes an old one by a new entry.

`README.md`, `CLAUDE.md` and `.github/copilot-instructions.md` point readers here.

## Ownership first

Before adding code, find the existing owner and all of its consumers. Extend that owner or its public
contract instead of creating a parallel implementation in a caller. The composition root is `main.go`;
backend owners live below `internal/`; frontend composition lives below `frontend/src/`. The
architecture map is the starting point for this search.

The Go backend is authoritative. The Redux store under `frontend/src/logic/store/` is a disposable
projection. Generated Wails bindings under `frontend/wailsjs/` are regenerated by the build. Only
`frontend/src/logic/adapter/` crosses from the frontend into those bindings. Shared UI components
receive props or primitive context and do not reach into the store, adapter or action registry.

Before adding a UI widget, hook, Go type or utility, search `frontend/src/ui/` and the relevant
`internal/` package for one that can be reused or extended with a prop, variant or parameter.

## Development loop

1. Orient: read the relevant `openspec/specs/` capabilities and the active change's artifacts.
2. Before the first production edit of a change, run `scripts/baseline` and confirm that every stage
   ran. A non-zero stage that collected nothing, or a required test count that is unavailable, is
   unreliable, not clean; fix that runner before using the record. `scripts/baseline` names its
   record after the current branch.
3. Work on the change branch or a task branch (see "Git workflow"), implement only the approved
   scope, and keep tests in `tests/go/` or `frontend/tests/` unless the task explicitly names a
   white-box test.
4. Run the narrowest relevant checks while working, then the full six-stage verification before
   calling a task complete. Compare with the baseline only through `scripts/baseline --compare`.
   A green stage is necessary but not sufficient: trace each requirement to the code path that
   implements it, make sure edge cases have tests, and start the real application to exercise the
   behaviour. Outside a Claude or Codex app session, check whether computer-use tooling is available;
   if not, ask the user to perform the real-app check in an app session.
5. Review the diff for ownership, public-surface documentation, generated-file drift and unrelated
   changes. Finish the task as described in "Git workflow".

## Git workflow

1. Every new OpenSpec change gets its own change branch, `feature/<change-name>`, created from `master`
   when the change is proposed or first applied. All of the change's work lands on it.
2. A task that could reasonably need several commits gets a task branch,
   `feature/<change-name>-<task>`, created from the change branch. A small task is committed on the
   change branch directly.
3. A task is finished only when it is implemented, verified, its docs are updated and it is marked
   done in `tasks.md`. Then commit it with a Conventional Commit message and, if a task branch was
   used, squash-merge that branch back into the change branch.
4. When every task is done and the user asks to archive, run the archive on the change branch and
   commit it there. Then ask the user whether to squash-merge the change branch into `master` or keep
   it unmerged. Never merge into `master` without that answer.
5. Every merge is a squash merge (`git merge --squash`, or `gh pr merge --squash`).

The six verification stages are Lint, Format, Build, Unit, Integration and E2E, run by
`scripts/verify` (single stage: `scripts/verify lint`; `--skip e2e`). Other entry points are
`scripts/build` (`setup`, `setup --with-browser`, `dev`), `scripts/test`, `scripts/format`
(`--check`) and `scripts/baseline`; `just --list` shows the optional aliases. Raw reports remain
under `.local_tmp_files/runs/<run-id>/`.

| Stage       | What it establishes                                                                                         |
| ----------- | ----------------------------------------------------------------------------------------------------------- |
| Lint        | Go and TypeScript checks, architecture boundaries, token rules, repository rules and referenced-path rules. |
| Format      | The repository's Go, Prettier and shell formatting policy.                                                  |
| Build       | Generated bindings, generated themes, production build, bundle policy and a clean tree.                     |
| Unit        | Fast Go and frontend unit behaviour.                                                                        |
| Integration | Go and frontend integration behaviour, including persistence and bridge seams.                              |
| E2E         | Real-backend browser behaviour and user journeys.                                                           |

## Working style

Keep the orchestrating context focused on decisions, not execution. Delegate coding, testing, review,
research and other context-heavy work to sub-agents. When a loaded skill's workflow matches the task
(brainstorming before ambiguous work, systematic-debugging before a fix, test-driven-development
before writing code, code review before calling work done), use it. The remaining engineering rules
(reuse, KISS/YAGNI/DRY/SOLID, TDD, tests over mocks, task shape) are in `openspec/config.yaml`.

Pause and ask when a decision would materially change product behaviour, expand destructive scope,
or create a durable architectural trade-off, or when the specs do not define the required behaviour.
Include the evidence found and a recommended default.

## Evidence and handoff

A task is complete only when its requirements have evidence, its named tests pass, the relevant
verification stages are green against the baseline, and the implementation matches the specs.
Record public-surface changes in the change's artifacts, `docs/index.md` or `docs/architecture.md`.
State the verified result, any pre-existing findings, and the next task or decision needed.
