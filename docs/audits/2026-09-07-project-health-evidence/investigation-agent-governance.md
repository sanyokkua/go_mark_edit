## New findings with source evidence

### G-1 — Broad stop rules make routine engineering an approval dependency

- `AGENTS.md:14–17` says to stop whenever a spec is silent on something that must be decided; `:36–40` repeats the broad exception despite saying “Advance without asking.” `:21–30` prohibits feature code before the full six-phase PLAN stage.
- The constitution, `.specify/memory/constitution.md:23–31`, stops delivery on a contradiction; `:143–145` requires an architecture decision for “Complexity” without a threshold; `:149–160` prescribes exact requirement/task/evidence mapping and full phase checks. `:175–186` requires preapproved amendments, semantic versions, a Sync Impact Report, constitution checks in every review and the constitution workflow as its only editor.
- Legacy `.agents/commands/build-story.md:10–23` blocks on empty template sections or missing rule-to-test rows and expressly forbids the implementer from filling the gap. `:76–82,144–148` treats every unlisted detail as a specification gap; routine changes to a shared component are named as potential unauthorized widening. `.agents/commands/plan-story.md:38–40` sets a hard five-rule maximum and asks the owner to approve the split.
- Generated `.agents/skills/speckit-implement/SKILL.md:59–91` scans every checklist, then stops for owner permission if any checkbox is open, before reading the implementation context at `:93–100`. It cannot distinguish a relevant unresolved product choice from unrelated incomplete review paperwork at that point.
- The optional workflow asset `.specify/workflows/speckit/workflow.yml:50–66` supplies approval gates after spec and plan; its registry only declares this bundled workflow (`workflow-registry.json:5–10`). It is not proof that this workflow ran or gates were seen in the audited history.

Consequence: a task can be fully authorized and technically understood yet stop on ceremony; another task may satisfy the ceremony while still failing its user journey. This is independent of missing commands in PR-2. Preserve escalation of a real conflict affecting behavior/data; remove blanket escalation for reversible implementation details. A missing diagnostic or test dependency should block the affected assurance claim, not every independent authorized activity. Retained optional skills must honor session authorization rather than silently reinstating routine permission prompts.

### G-2 — Fixed task and evidence units reward local completion over shared ownership

- `AGENTS.md:27,90–105` requires one task = one branch = one commit, a new task subbranch before touching a file, gate/squash/delete after each task. The generated tasks template instead allows commits “after each task or logical group” (`.specify/templates/tasks-template.md:250`); neither granularity is a product invariant.
- `AGENTS.md:53–54` frames baseline differences as blame (“not yours” / “is”). Its useful neighboring rule is honest measurement (`:55–60`), not ownership by timing. A baseline identifies preexisting defects; it does not make those defects acceptable or require resolving every unrelated historical defect before useful work.
- The constitution requires complete copied requirements/exact locations/named proving tests for every rule (`:36–43`), maps each requirement to exactly one task (`:152–153`) and requires each phase's named-test review, traceability/spec checks and packaged walkthrough (`:119–124,156–163`).
- `.agents/commands/plan-story.md:52–83` copies every clause/table/example and counts source/copy lines; `:112–132` repeats every applicable architecture rule via an exhaustive glob table. `:149–168` adds per-rule test names, colocated test paths and dead `spec-check` validation. This directly duplicates authority and creates stale derivatives.
- `docs/delivery/work/DOD_TEMPLATE.md:27–40` has identical mechanical rows for every story, including every changed source file being touched by a test, while `:68–70` says the Proves tag is not validated. The active legacy command still claims it is validated (`plan-story.md:165–168`; `build-story.md:118–119`).
- `AGENTS.md:143–162` mandates the same Next step form for every advancing turn, even after completion; `:109–125` mandates delegation for whole categories and an eight-agent cap irrespective of task size or available tools. These are operating preferences, not evidence of product correctness.

Consequence: a common fix spanning several consumers competes with a narrowly declared task path; explanation and code become ID led; bookkeeping is repeated even where it offers no assurance. Keep reviewable changes and accurate verification; allow logical commits and sensible branch isolation, with protected-branch and user-work safeguards. Keep tests named by behavior and choose evidence at the boundary that owns it, permitting one meaningful test to cover multiple acceptance statements and one important scenario to need several tests. Avoid quotas, a test per changed file and one-to-one claim/task/test cardinality.

Existing audit RC-6/RC-7 diagnoses the history, but the proposed future guidance should explicitly remove the machinery which regenerates it. Existing RF-D5's optional comment/ledger mapping already points the right way.

### G-3 — Root guidance does not state the owner's reuse and simplicity decision

`AGENTS.md` describes backend projection ownership (`:169–173`), tokens (`:174–176`) and the action registry (`:211–214`) but has no comparable instruction to inspect and extend the existing common component/policy before creating a private copy. The constitution's UI principle (`:95–106`) requires registries/tokens/accessibility, but does not establish the shared framing/lifecycle/component ownership the owner now requests.

`docs/delivery/architecture/structure.md:78` suggests a new backend package with handler/service/repository for a new capability; `:86` locates a reusable control; `:91` says to inline a shared helper until a second caller exists. These instructions identify folders or caller count rather than checking the actual ownership of a repeated concern. The original frontend document already prescribed common controls and Radix wrappers (`50d692d:specification/02_Architecture/03_FRONTEND_REACT.md:31–43`, dependency explanation immediately below). Reuse is established intent, not a reason to build a new generic framework.

Proposed principle: before adding behavior or styling, find its current owner and consumers; reuse or extend the existing component, command, token, validation, persistence or lifecycle seam. Put common policy in one place and pass content/state/variants through explicit inputs. Preserve legitimate engine differences (Monaco versus Markdown renderer), product semantics and deferred capabilities. Use idiomatic Go/React/TypeScript for the pinned stack; prefer composition and focused interfaces over extra layers, universal factories or configurable frameworks. Introduce an abstraction when an existing common responsibility or concrete consumer makes it useful; do not duplicate simply because the present task shows only one caller, and do not abstract solely for a hypothetical future caller.

KISS/DRY/SOLID should mean this behavior, not a checklist of acronyms or an arbitrary file/function limit. Apply the owner-approved Popup/Bar/Pane/StatusBar/Sidebar family direction without treating every example API as immutable. RF-B13's file-category rule is also a proposal to assess by cohesion and independent change, not a new automated ban on a file containing composition plus a small callback.

## Minimal guidance shape (proposal, not a new file or line quota)

The root should answer five practical questions in connected prose or a few short bullets:

- What product are we building, what is currently in scope, and where is the current accepted intent? Latest explicit owner decisions take precedence over stale project process.
- What must survive changes? Offline bundled operation, private local data, safe writes/close/recovery, backend ownership, sanitization, accessible/localized consistent UI and the declared cross-platform support.
- How should a change be designed? Inspect existing implementation and consumers first; extend common components and policy owners; keep idiomatic simple code with explicit boundaries, useful composition and no duplicate sources of truth or speculative framework.
- When should the agent proceed or ask? Proceed through diagnosis, reversible implementation and appropriate checks within scope; ask only when a real unresolved product/irreversible choice affects the outcome, and continue independent work.
- How does the agent establish completion? Use the maintained command entry points and evidence appropriate to the changed behavior; inspect actual results and host boundaries; summarize what changed, what was verified and remaining limits. Never equate bookkeeping, a mocked backend or an unexecuted check with a working native application.

This is not a replacement product specification. Numeric product limits and safety-relevant algorithms can remain exact in their authoritative contracts; “remove rigid limits” here concerns arbitrary development ceremony, not deleting real document-size bounds or durability guarantees.
