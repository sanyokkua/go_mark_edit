## Finding A — preview anchors bypass application navigation and document resolution

**High priority; high confidence in source gap. The exact owner incident remains unconfirmed.**

The production trace is `EditorView.tsx:517` → `LivePreview` (`:279`, `:287`, `:319`) → `PreviewPane.tsx:139` → `MarkdownView.tsx:33–41`. `MarkdownViewProps` contains only `source` (`:11–13`). Neither that component nor its preview parents receives a document path or a link-activation callback. The shared `markdownComponents` map supplies **only an image override** (`frontend/src/logic/markdown/renderer.ts:39–53`). There is no anchor override, click prevention, explicit target, document-relative URL resolver, or dispatch into the file lifecycle. Focused searches found no application `BrowserOpenURL`/`window.open`/navigation interception for preview links.

This is already a shared-renderer boundary: the needed common behavior has a natural single owner. The gap is missing link policy/dispatch there, not six unrelated preview implementations. A relative link such as `[Next](./next.md)` stays an ordinary `<a href="./next.md">`; browser URL resolution uses the app page location, not the Markdown document's filesystem directory. An absolute filesystem-looking path such as `/Users/.../note.md` similarly denotes an app-origin URL path. Clicking an ordinary eligible anchor is therefore left to the webview's default document navigation, instead of invoking the application's document-open/activation flow.

**Do not confuse a “file link” with the `file:` scheme.** The inherited sanitizer allows `http`, `https`, `irc`, `ircs`, `mailto`, and `xmpp` (`frontend/node_modules/hast-util-sanitize/lib/schema.js:141–145`); its `safeProtocol` preserves relative/fragment URLs but rejects an unlisted explicit scheme (`lib/index.js:672–714`). React Markdown's default URL transform independently preserves relative URLs and those allowed protocols (`frontend/node_modules/react-markdown/lib/index.js:124`, `:421–443`). Thus literal `file:` and `javascript:` targets are stripped with this source. Relative/root-relative local-looking targets, fragments, and HTTPS links remain relevant cases. Do not loosen the sanitizer to repair navigation.

### Native and development consequences are different

`main.go:160–203` provides embedded assets (`:171–173`) and lifecycle callbacks, with no application asset handler/middleware or navigation policy. The pinned macOS Wails implementation starts at `wails://wails/` (`internal/frontend/desktop/darwin/frontend.go:40`, `:98`; dev setup can change host/URL at `:104–110`). It sets a WKNavigationDelegate (`WailsContext.m:315`) and reports `DomReady` after navigation (`:509–510`), but implements no `decidePolicyForNavigationAction` interception. Its binding-origin validator (`frontend.go:171–193`) rejects disallowed bridge messages; **that is not a navigation blocker** and does not establish that an ordinary same-origin path change loses bridge permission.

The following dependency references are under `/Users/ok/go/pkg/mod/github.com/wailsapp/wails/v2@v2.15.0/`:

* **Embedded build:** `pkg/assetserver/assethandler.go:81–97` looks up the URL in embedded assets and returns 404 if absent and no custom handler exists. There is no arbitrary `.md` → app-index fallback in that handler. Unknown relative Markdown targets therefore request the wrong resource; the exact WKWebView error/blank-page behavior needs native observation. Do not claim that every packaged link click necessarily renders StartupFailure.
* **Wails development with Vite:** `wails.json:7–8` runs the frontend in `--mode wails` and discovers its dev server. Wails `internal/app/app_dev.go:117–146` installs the external proxy; `pkg/assetserver/assethandler_external.go:25–32,64–69` forwards GET paths. `internal/frontend/devserver/devserver.go:95–106` wraps that handler in the dev asset server. Crucially, `pkg/assetserver/assetserver.go:140–183,200–205,248–254` injects runtime and IPC scripts only when the **requested path** ends in `/` or `/index.html`.
* The installed Vite SPA fallback accepts an HTML navigation to a missing path and rewrites it to `/index.html` (`frontend/node_modules/vite/dist/node/chunks/config.js:22092–22134`); the project leaves default SPA behavior enabled. Consequently an unknown target such as `/next.md` can receive React's app index from Vite while bypassing Wails's path-based runtime injection. React then starts again (`frontend/src/main.tsx:13–17`) without injected `window.runtime`/`window.go`. Generated runtime event functions directly dereference `window.runtime` (`frontend/wailsjs/runtime/runtime.js:39–44`), and generated settings/retry calls directly dereference `window.go` (`frontend/wailsjs/go/settings/SettingsHandler.js:5–6`; `.../application/ApplicationHandler.js:13–18`). **This is a concrete, source-supported candidate chain for the reported failure screen, conditional on dev launch and the actual clicked/resolved target. It is not a reproduced incident conclusion.**
* **Ordinary mock-backed dev-ui:** `frontend/vite.config.ts:34–49` resolves Wails calls to mock modules outside `wails`/`production` modes. An accidental SPA reload can therefore bootstrap successfully through mocks and conceal the native/development bridge failure. Passing Chromium mock tests does not establish native link containment.

## Finding B — the failure screen loses the real failure and Retry assumes an intact bridge

**Medium priority confirmed diagnostic/recovery gap; this is not evidence that SQLite/settings caused the incident.**

`frontend/src/App.tsx:165–186` catches failures from importing adapters, model bootstrap, settings bootstrap, and WindowReady, discards the error, and returns only `{status:'failed'}`. `appModelProjection.ts:55–100` independently discards errors in event subscription, GetState, or required application-version validation. The displayed catalogue text is always “GoMarkEdit could not initialize its local settings. Please try again.” (`frontend/src/i18n/locales/en.json:69`; `StartupFailure.tsx:17–22`). It cannot identify the failing subsystem or prove settings corruption.

`App.tsx:1890–1932` runs bootstrap on App mount and handles its failed result; `:1995–2000` renders StartupFailure and routes Retry through the same bootstrap helper. Retry first invokes `applicationAdapter.retryStartup()` (`:173–174`), which needs `window.go`; it does not reload the canonical application URL, re-inject missing scripts, or reconnect a lost bridge (`windowAdapter.ts:38–57`). Thus in the missing-runtime candidate above, repeated Retry cannot repair the missing capability and returns to the same generic failure screen.

The ready preview cannot itself set bootstrap status to failed through `MarkdownView`; the inspected failure assignment is inside bootstrap handling. A post-click return to StartupFailure is therefore consistent with an App remount/rebootstrap. It does **not** establish a blocked native thread. Ordinary close is a separate dependency on frontend lifecycle readiness (`App.tsx:1962–1969`); the shutdown reviewer owns its full causal analysis. No source evidence here establishes why macOS Force Quit reportedly failed or why htop was needed, and no data-loss claim is established.

## Requirement and history boundaries

Original baseline `50d692d`, `specification/01_Product/05_RENDERING_AND_EXTENSIONS.md:69–84`, describes shared components, optional link/image adjustment through the guarded asset/remote-content policy, and mandatory sanitization. It does **not** prescribe local-link tab selection or external-browser activation. Current legacy `docs/delivery/spec/product/rendering-rich-documents.md:38–44,221–224` requires sanitization and inert dangerous URLs. Migrated `specs/001-gomarkedit-product/spec.md:513–520` requires GFM/autolinks and one rendering interpretation; its `:605` external-link destination clause concerns PDF output. `specs/002-editor-stage-formatting/spec.md:283–285` concerns the **Link insertion action**, not preview activation. Image asset containment clauses are not a complete document-link navigation contract. Bounded original/current searches found no explicit normal-link click routing contract.

The missing routing predates recent popup work: `96672e1` (STORY-014, 2026-07-21) introduced the source-only MarkdownView and img-only override. `59b379a` (STORY-031, 2026-07-23) restored GFM footnotes and matching fragment IDs without introducing link activation. `544372d` memoized MarkdownView for performance. These are not evidence of a recent link-policy regression.

Before implementation, define fragment/local-document/external/unsupported target policy, including local target tab behavior. Keep document resolution and command dispatch at a shared boundary; preserve fragment and footnote navigation and the existing sanitizer. Prevent document content from replacing the application page. Do not invent a Wails navigation option or reuse a recent-file-only command as an arbitrary-path API without checking its contract.
